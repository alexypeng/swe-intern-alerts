# Eightfold source research

Research snapshot: 2026-10-09. Research is followed by a local PayPal-only adapter implementation (2026-10-12). Its board is not enabled pending runner validation; shared classification is unchanged.

## Recommendation

Start with **PayPal**, already approved in `config.toml`'s fallback company list, using its current public PCSx frontend search API. Anonymous search and field mapping work. A complete anonymous scan now validates pagination for this snapshot and finds zero internship-title candidates. One active role's detail and public page corroborate identity, URL and posted date. Positive internship eligibility, alternate URL aliases and GitHub-runner access remain unverified. Do not use the documented authenticated customer API for anonymous polling, and do not assume an old public endpoint or another tenant has the same access behavior.

## Sources and access evidence

The current [PayPal careers tenant](https://paypal.eightfold.ai/careers?domain=paypal.com) returned anonymous HTTP 200 using a plain GET without credentials or retained cookies. Its HTML bootstraps `domain=paypal.com` and loads the shared [PCSx frontend JavaScript](https://paypal.eightfold.ai/gen/js/pcsxPwa.fa5d073d8912644a.js). The same bundle was downloaded from [Qualcomm's first-party careers host](https://careers.qualcomm.com/gen/js/pcsxPwa.fa5d073d8912644a.js); PayPal HTML references precisely that bundle path/hash. Qualcomm is illustrative platform evidence, **not an approved company addition**.

The bundle constructs `GET /api/pcsx/search` with `domain`, `query`, `location`, `start`, optional `sort_by`, repeated `filter_<name>` parameters, and optional `hl`. It reads `data.count`, `data.positions`, `filterDef`, and `resultsMetaData`. It also calls `/api/pcsx/position_details?position_id=<numeric-id>&domain=<domain>&hl=en`. These are observed private frontend contracts, not a documented stability guarantee. [Frontend source](https://careers.qualcomm.com/gen/js/pcsxPwa.fa5d073d8912644a.js). The detail helper returns `data` directly as the position and separately reads `metadata.isFallback`; successful HTTP status alone therefore should not establish valid requested-job identity.

A live anonymous [PayPal search request](https://paypal.eightfold.ai/api/pcsx/search?domain=paypal.com&query=&location=&start=0&sort_by=timestamp) returned HTTP 200, an envelope with `status`, `error`, `data`, `metadata`, count **303**, and **10** positions. Returned `sortBy` was `timestamp`, and `resultsMetaData.usedFuzzSearch` was false. A subsequent bounded scan fetched all 303 unique rows across 31 pages with exact expected page lengths (30 ten-row pages plus a three-row final page), stable counts, and a matching final response in **3.709 seconds** using at most four workers. This is local snapshot evidence, not a runner benchmark or a publication-latency measurement. The legacy `/api/apply/v2/jobs` route returned HTTP 403 in a separate parent-agent probe; this does not invalidate the working PCSx endpoint or establish that the legacy route always blocks.

The saved PayPal HTML bootstrap config sets `basePositionFq` to public/external/nonconfidential postings and excludes ATS statuses `CLOSED` and `FILLED`. It also sets `excludePrivatePositions=true`, and disables automatic location filling. This explains the intended public-search scope; it does not independently prove that the API returns every open posting. Its job-detail display config uses fields such as `display_job_id` and `efcustom_text_time_type`, whose display labels cannot by themselves establish internship eligibility. [PayPal careers HTML](https://paypal.eightfold.ai/careers?domain=paypal.com).

Eightfold's documented [List Positions API](https://apidocs.eightfold.ai/reference/list_position) requires Authorization. The [authorization guide](https://apidocs.eightfold.ai/docs/eightfold-api-authorization-guide) describes customer administration and API keys/permissions. Treat this as a different API from public careers search.

Intel is approved but was **not verified as an Eightfold tenant**: a speculative `intel.eightfold.ai` hostname failed DNS both inside and outside the sandbox. First-party [Intel job pages](https://intel.wd1.myworkdayjobs.com/en-US/External/job/Process-Integration-and-Yield-Intern_JR0282666) show Workday. A guessed hostname failure is not evidence that Intel has no Eightfold services; it is sufficient reason to avoid designing an Intel Eightfold board from that guess.

## Completeness, eligibility, and identity

The completed scan validates observed offset behavior and all 303 count-backed results. All search records had the same 15 fields, a nonempty posting timestamp, and unique `atsJobId` values. There were zero shared internship-title candidates and no broader title signals for student, university, early, graduate, apprentice, trainee, campus, summer, 2026, 2027, or entry. This does **not** prove there are no internships hidden only in descriptions or omitted by the public-search scope, stable behavior across future polls, or supported page-size overrides. The downloaded frontend sends `start`, but sends no page-size parameter in the observed search function. A future adapter should retain the validated ten-row page size and fetch all pages with at most four workers; require exact expected page lengths, unchanged counts, unique numeric IDs, and a matching final count response. Any failed required page or candidate detail rejects the whole board, preserving the plan's successful-first-poll boundary. Count checks cannot detect every same-count change.

Select internship candidates initially with the shared title regex (`intern`, `internship`, `co-op`, `coop`) and graduate-title exclusion. Validate that against a complete search scan and details before proposing native filters or employment-label classification. PayPal's [official university page](https://careers.pypl.com/university-hiring/north-america-latin-america/default.aspx) describes general advertisements differentiated by focus and both undergraduate and graduate opportunities. General pools may therefore be legitimate postings; inspect actual role titles and requirements rather than assuming every university listing is undergraduate eligible.

The frontend parses numeric job identity from `/careers/job/<id>-<slug>` and the `pid` query parameter. Thus the UI itself accepts multiple public URL forms. The repository's generic normalizer currently leaves nontracking query parameters intact, so a direct `/careers/job/<id>` URL and a fallback `/careers?pid=<id>&domain=paypal.com` can remain distinct. That is a **potential deduplication gap**, not yet a reproduced duplicate. The current Simplify file contains one PayPal record: `Software Engineer Intern`, ID `30829caf-2d43-4e4c-aeb6-aa37a19f224b`, `active=false`, `is_visible=true`, URL `https://paypal.eightfold.ai/careers/job/274922260559`, and Bachelor's/Master's degrees. It is absent from all 303 direct results and is not an eligible active fallback; its URL already uses the direct canonical path shape, so this record does not reproduce a query/path alias mismatch. Its [official detail endpoint](https://paypal.eightfold.ai/api/pcsx/position_details?domain=paypal.com&position_id=274922260559&hl=en) returned HTTP 404, while its [public HTML page](https://paypal.eightfold.ai/careers/job/274922260559) returned 200 without JobPosting JSON-LD. These observations agree with its absence from search and inactive fallback status, but do not prove why it was removed. HTML 200 alone does not establish that a job is open. [Simplify data](https://raw.githubusercontent.com/SimplifyJobs/Summer2027-Internships/dev/.github/scripts/listings.json). Compare verified canonical/details/application links before defining a narrow, company-specific alias rule. Preserve the original application URL for Discord. [Frontend URL parsing source](https://careers.qualcomm.com/gen/js/pcsxPwa.fa5d073d8912644a.js).

Supplementary keyword probes returned `intern=1` (Manager, Internal Controls), `internship=0`, `co-op=0`, `coop=42` (first ten rows had senior-role titles), and `university=0`. The `coop` query was not fully paginated; the unfiltered scan already contains every count-backed public result. Keywords can match unrelated roles and do not replace the shared title rule. ## Implementation (2026-10-12)

`src/intern_alerts/sources/eightfold.py` scans every count-backed public search page, with ten-row pages and at most four outstanding requests. It rejects invalid API envelopes, fuzzy search, short/long pages, changing counts, repeated position IDs, invalid title/location/date/URL metadata, and a changed final first page. Counts above 10,000 fail as a bounded-scan guard, not as a verified API capacity. A failure returns no partial postings.

Search supplies every required Posting field, so this implementation returns all valid search rows without extra detail requests. The shared classifier uses existing title-based internship and graduate-title rules; it does not infer eligibility from descriptions, departments or Full Time labels. Remote locations retain their country restriction. No state schema, alias normalization, persistent cache or source-specific degree parser was added. The actual fallback URL uses the same canonical path, and ordinary tracking-parameter normalization provides deduplication for that form. Alternate query/slug aliases remain unverified.

Config accepts only `source="eightfold"`, `slug="paypal"`, `name="PayPal"` without host/partition/native-filter fields. The fetcher is registered in the existing pipeline; successful empty scans initialize silently, and failures do not initialize. The manual `.github/workflows/validate-paypal.yml` workflow fetches/classifies without webhooks or persistent state and fails on source errors. After committing/pushing, run it and inspect its source log before adding the PayPal board to `config.toml`.

Verification: 405 tests passed in 1.77s, including 29 added cases across source/configuration tests. The adapter live read-only check verified 319 search rows in 4.17s, with zero announceable postings; no messages or state writes. Both implementation reviews found no runtime defects. GitHub-runner access and a live positive internship example remain unverified.
